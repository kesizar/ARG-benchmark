# 宝亚保健有限公司准备说明

对应原始记录 `base664:0032`，本地任务 ID 为 `baoya`。旧任务标题为“宝亚”，原清单使用公司全称；身份关联依据是原入口 `wanwuyongyuan.github.io/baoya/` 与本地材料标注的 `wanwuyongyuan/baoya`，不是只按相似标题匹配。

## 资源与接入

这是多页面浏览器作品，内含虚构账户和客户端密码检查，没有真实账号、购买、后端和登录态依赖。使用本地静态服务器，新的浏览器上下文恢复初始状态。原材料保留于 `judge/baoya/source`，不会由游戏根目录托管。

已移除外部 Google 字体、Google Analytics 和访客徽章请求，使用原 CSS 的本地字体回退，布局视觉可能不同但文字和谜题判断不变。邀请函函数原来尝试给不存在的下载按钮绑定未定义函数；该异常发生在邀请函内容渲染后。本版本仅增加存在性检查，没有虚构下载文件或线索。变更和全文件哈希见 `tasks/baoya/provenance.json`。

`wushan.js` 虽然包含另一套小游戏，但没有被当前 `wushan.html` 引入；不能把它当成实际游戏谜题。`alert-timer.js` 与未链接的测试原型也不纳入故事流程。保留这些原始文件以便溯源。

## 全流程与分支

实际故事包含 18 个页面，详细页面和边见 `flow.json`。入口邮件可进入公司账户门户与邮箱登录。公司门户分为客户、三名员工账户；员工个人资料、简历、博客和加密邮箱提供相互关联的线索。老板邮箱提供景区链接，景区的隐藏入口打开代码排序游戏，成功后进入地图。

地图分为三种终局前路径：在限时内照抄 QTE 序列成功；按错键后进入解密输入；等到超时后进入同一个解密输入。后两种需要完成恺撒转换。三种路径均进入最终选择页，产生两个叙事结局。源码未发现另一个隐藏结局或永久死亡状态；错误登录、排序和解密均可重试。

## 判分

旧裁判存在两个问题：把“进入雾山”和“打开选择页”当成解谜得分，并把可跳过的员工或加密邮箱分支列入所有结局的必经门。当前区分为八个可证明的谜门：五个虚构身份登录、加密邮箱解锁、代码排序、恺撒转换。

从正常玩家界面到终局，老板邮箱和代码排序是必经门；其他账户分支和恺撒后备解密为 optional。不能仅因它们在预想攻略里出现，就把它们设成程序上必经。页面导航、邮件阅读、隐藏按钮发现和照抄 QTE 仅作为探索或操作事件。两种终局分别记录，暂不把没有明确评级的叙事选择擅自设为好坏。

成功证据来自实际目标页面与标题节点、动态生成的解锁后邮件列表、代码排序成功提示和解密成功反馈。每一步锁存结果，不把短答案输入本身当成整局通关。裁判侧复核文件在 `checkpoint-spec.json`。

## 验收边界

`verify_baoya.py` 读取游戏内原始答案仅用于私有工程验收，所有推进通过 BrowserHarness 的点击、输入、按键、返回、切换/关闭标签和等待动作完成。不注入状态，也不调用游戏的解锁或跳转函数。两类结局和 QTE 三种路径应从新 context 验证；判分以 `verification/acceptance.json` 的最终结果为准，不当成模型成绩。

游戏资源包是 `packs/baoya.resources.zip`，独立评测包是 `packs/baoya.prepared.zip`，后者包含版本固定的 harness、配置、裁判和私有验收脚本。Python 依赖与浏览器是明确列出的基础环境，不假装随 ZIP 提供。验收还需在新解压目录、新端口重跑，记录独立部署证据。

## 内容审核问题

普通客户的密码提示与实际接受的值之间推导关系不清晰，需要人工确认。代码排序的内在线索偏弱，而提示按钮直接泄露答案，不应据此认定题目较难。QTE 是限时照抄操作，故不计推理主分；当前截图+文本观察对限时反应存在额外约束。已提供可推理解密的后备路径，但不能把这种差异隐去。

因此工程通过后仍应保持“内容审核待确认”，而不是将这条直接标为正式收录完成。
