# ARG Benchmark 项目与测评机制说明

面向论文撰写同事的交接文档

修订日期 2026年11月2日

## 1 项目定位与当前结论

ARG Benchmark 以 ARG、网页解谜、密室、文字冒险和静态谜题等交互任务为载体，研究模型能否在有限观察、受限动作和固定预算下，持续搜集信息、建立假设、推进环境状态并完成指定目标。ARG 指 Alternate Reality Game，即以故事、线索和分散材料构成的实境解谜游戏；项目实际任务范围比狭义 ARG 更广，因此论文需说明纳入的游戏类型。

测量单位是“特定版本任务的一次独立运行”，而不是一条聊天回答。模型在每一步接收玩家侧信息并提出一个动作，由统一运行框架执行；独立裁判根据真实环境状态判定进展和成功。论文可以把项目定位为面向多步交互解谜的智能体评测框架及任务资源体系。[S01–S05]

项目实现由统一运行框架、任务配置、作品资源、独立裁判和结果汇总组成。本文重点说明任务怎样执行、模型能看到什么、哪些能力与任务有关，以及单局结果怎样转化为最终指标。

**论文主指标采用指定目标成功率 SR 与路线进度 Progress。** 进入某个结局、完成全部中间门、说出“任务完成”，都不能自动替代指定目标成功。辅助指标包括重复成功稳定性 pass³、适用题集上的好结局率与终局失败率，以及动作、时间和 token 消耗。[S02、S04、S06]

阅读重点：第2节解释能力含义，第3节解释模型的输入与操作，第4节说明单局评分，第5节说明重复实验和汇总，第6节给出论文组织建议。附录A列出运行入口，附录B说明正文各项规则在项目中的出处。

## 2 能够验证的能力及其解释边界

本 benchmark 首先观察任务完成行为，再根据任务设计和裁判证据解释其涉及的能力。某项能力只有在完成任务必须依赖它、且相应行为有可核查证据时，才应成为该题的能力标签。仅凭题材、文本长度或“有多张页面”不能完成能力标注。[S02、S03]

### 2.1 叙事证据推理

模型需要从日志、人物资料、对话、档案或不同页面中抽取事实，区分相关与无关线索，建立人物、时间、事件之间的关系，再据此形成答案或行动。可支持的证据是：某个通过条件必须联合多处材料，正确答案与错误答案能被裁判区分，并且正常通关轨迹展示了对应的证据使用机会。

《灯塔剧社戏单档》包含跨材料推导后台凭证、复原戏单的联合判断。项目说明也指出其中若干内容在后台笔记中已直接给出，且原作有逐字段错误反馈，因此不能把所有填写项都算成独立推理题，也不能仅凭通关宣称完成了无提示推理。[S10]

### 2.2 长程规划

模型需要确定先后顺序，识别解锁依赖，在多条路线之间安排子目标，必要时回访页面、修正计划并控制预算。可支持的证据应包括真实的前置依赖、跨多个有效操作的路线，以及到达目标的完整轨迹。大量点击或长时间运行本身不等于高规划难度；冗余动作可能来自界面使用困难。

### 2.3 状态追踪

模型需要持续维护已读材料、已验证假设、已有道具、权限、账号、分支和完成阶段，避免重复操作或使用过期状态。项目可以借助轨迹与裁判锁存记录，检查这些状态是否实际被正确推进。默认会保留此前模型回复，因此这里测到的是在给定历史支持下的状态管理能力，不能称为脱离外部记忆的纯记忆能力。[S05]

### 2.4 交互探索

模型需要判断下一步查看什么、操作哪个控件、如何在反馈后改变探索方向。网页中表现为点击、输入、滚动、拖动和标签页管理；文字冒险中表现为合法命令与反馈解释。动作轨迹能揭示探索是否有效，但目前没有通用于所有题目的状态覆盖率指标；页面访问数和点击数不能替代探索质量。[S02、S05]

### 2.5 视觉理解及其他能力

主测统一采用截图、可见文字和可交互元素信息共同构成的B档输入，可以承载视觉定位、图文对应、空间关系等要求。由于模型也能使用提取的文字和元素编号，成功结果反映这一统一输入条件下的综合表现，不能单独归因为视觉能力。音频理解、开放互联网检索、通用代码执行和任意桌面操作都不是全项目统一开放的能力；只有明确支持、已验收的子任务才能作相应讨论。

各能力可以重叠。按能力子集报告的仍然是任务成功率，不是对隐含认知能力的直接测量。模型失败也不能单凭最终零分归因为“不会推理”：感知、控制、探索、状态维护和预算都会影响结果。

## 3 任务运行与模型观察

### 3.1 运行环境

游戏类别 category 与运行层 runtime_layer 是两个独立维度。L1表示材料、逻辑和状态能够本地提供，包括镜像网页、静态材料和本地解释器；L3表示依赖真实在线页面、远端服务或账号状态。当前新配置使用L1与L3，旧L2记录保留历史身份，不重新标成已符合新规则。[S01]

L3依然使用明确主机白名单，并不开放任意互联网或攻略搜索。多域名作品可在显式白名单内运行。每个游戏选用适合的运行层后，对所有比较模型保持一致；L1与L3通常对应不同题目组成，分层成绩不能直接解释成运行层的因果效应。模型API属于评测基础设施，不属于游戏可访问网络。

### 3.2 一局如何执行

任务配置与资源 → 启动新环境 → 提供目标及初始观察 → 模型给出一个JSON动作 → 校验并执行 → 裁判读取环境 → 保存观察和判分 → 继续或终止。

模型侧只接触任务允许的观察与动作。裁判可以读取浏览器状态或其他可信信号；裁判正文、答案校验规则、检查点名称与数量不进入模型提示。judge目录及评测代码不能由游戏服务器公开托管。[S03–S05]

运行框架支持浏览器、文字冒险、静态题，以及已有配置中的棋盘和场景工具适配器；不同适配器的完成度须分别验收。computer_use字段不代表模型获得全操作系统控制。浏览器模型也不能自行执行JavaScript或读取任意文件。

### 3.3 主测统一采用B档输入

“观察”是模型决定下一步动作前收到的环境信息。当前主测统一使用B档，它是输入配置的名称，不是评分等级，也不是本轮实验需要比较的自变量。同一题的所有比较模型使用相同的B档输入规则。[S05、S07]

B档每步提供当前视口截图、玩家可见的页面文字、可交互元素信息，以及标签页、对话框、上一动作结果和剩余预算等辅助信息；地址是否显示由配置决定。模型由此既能阅读材料，也能观察布局并操作页面。它例如收到“收件箱”按钮的临时编号3，同时看到该按钮在截图中的位置，就可以按编号点击，或根据截图执行坐标点击。元素编号以最新观察为准，不是固定的页面控件ID。

论文需要说明B档，是为了准确界定模型获得了什么帮助、读者怎样复现实验，以及不同模型是否在一致的信息条件下比较。例如只给某个模型截图、却给另一个模型截图加文字和控件编号，就不属于相同输入条件。截图、文字提取范围、元素信息、视口和历史规则都应保持一致；require_images=true用于阻止图像发送失败后静默变成纯文字运行。

因此，本轮成绩应解释为“模型在统一图文与元素辅助输入下完成交互解谜的能力”，而不是仅凭截图的视觉操作成绩。框架还保留A档和C档两种可选配置，供其他使用场景扩展；本轮主测不使用它们，也不设置A/B/C对照实验。

### 3.4 观察历史与状态重置

可见文字会过滤脚本和隐藏节点，文字范围可配置为整页或视口。默认保留最近4步的完整观察、最多2张历史截图，再加当前截图；更早步骤保留动作、结果、URL或标题以及此前模型回复。这里的“最近4步”不是把整局记忆全部截断到4步。[S05]

浏览器每局使用新context隔离本地存储。L3服务器状态和账号还需要另外的重置方案，新context不能替代远端状态重置。同题跨模型必须使用一致的观察历史与初始状态。

## 4 单局怎样评分

### 4.1 先分清两个主指标

一局结束后，首先回答两个问题：“指定目标是否完成”和“完成了多少可以核查的中间步骤”。前者对应目标成功值x，只有0或1；后者对应路线进度p，可以是0到1之间的数，也可能因没有可计分路线而缺失。多次运行后再把x平均成成功率SR。[S04、S06]

例如目标是“找到正确档案并提交最终结论”，模型读完所有档案但没有提交正确结论，x仍为0；如果已完成可计分的中间步骤，p可以大于0。两者分别表示是否完成任务和推进程度，不能相加成一个总分。

当前正式运行使用target_v1。旧的legacy评分仍用于兼容历史任务，不能将旧进度值直接混进新协议的论文主表。下面都按target_v1解释。

### 4.2 指定目标怎样算成功

每题在运行前明确题面目标，并在私有裁判中配置target_success。模型声称“已经成功”、写出一段解释或完成若干点击，都不能自行改变成功值。当前代码支持四类客观条件：[S04]

1. **答案条件**：题目要求通过专用答案接口作答，裁判核对正确答案。只有配置把answer设为成功条件时，答案正确才使x=1。
2. **指定路线结局**：题目列出可算成功的路线ID，真实触发其中任一路线的结局条件后，x=1。未被列入的普通或其他结局，不能仅因“出现了结局”就算成功。
3. **单结局条件**：没有显式多路线的任务，可以将经过核查的单一游戏结局设为成功条件。
4. **专用状态条件**：通过hook_condition引用一个预先定义的真实成功状态，适用于目标已完成但没有传统结局画面的任务。

同时配置多个成功条件时，当前实现按“或”处理，即任一个满足就可成功。如果目标要求多个要求同时满足，应先把它们写进同一个联合状态条件，而不能把它们分别并列后误以为按“且”判断。bad路线不允许列为成功路线；一旦裁判记录终局失败，目标成功值为0。

以下概念分别记录：target_success表示指定目标是否完成；ending_reached表示是否到达裁判记录的结局；ending_tier表示good、normal或bad等级；failure_reached表示是否发生不可继续的终局失败。它们不能互相替代。即使answer_correct为真，若该题指定目标是另一个真实结局，也不自动使target_success为真。

### 4.3 裁判依据什么授分

裁判通过hook读取环境信号。“hook”在这里就是一个预先写好的状态检测器，例如确认成功提示确实出现、已提交答案正确、档案确实解锁，或游戏存储中某个状态成立。当前支持URL、可见DOM、对话框、本地存储、请求记录及受信任脚本检查。裁判读取这些状态不代表模型也能读取它们；模型侧仍只收到允许的观察。[S04、S05]

专用答案接口可以先做NFKC字符归一化、去空白、转小写，再进行SHA-256比对。例如全角Ａ与A、大小写、无关空格可在这种规则下视为同一输入；同义词和其他合理答案不会凭语义自动获得认可，需要任务裁判事先支持。游戏内网页表单也不一定使用这个通用答案规则，要看具体题目的检测方式。

得分必须来自经过验证的条件。只打开某个页面、看到“提交”按钮或输入任意字符，不能代替答案被正确接受。页面里的隐藏模板、旧存档和无关提示也不能当成本局成功证据。

### 4.4 哪些中间步骤计入进度

任务预先定义检查点checkpoint，并赋予角色：

- **critical关键点**：有实质意义、属于路线要求的中间成果。例如正确推导凭证并解锁档案，或完成一个必要的证据匹配。当前公式按点等权计数，不根据“看起来难”临时加分。
- **optional可选点**：可完成的额外挑战或支线。会记录，但不进入target_v1的主Progress。
- **diagnostic诊断点和events事件**：帮助复盘，例如打开栏目、触发错误反馈、进入某页面。这些本身不增加主Progress。

关键点第一次满足条件时，裁判保存其ID和命中步数。相同关键点再命中不会重复加分。进入已解锁页面后返回，已获得的关键点也不会因为页面不再显示而被扣掉，这叫“锁存”。新的一局重新开始时，锁存记录应清空。

错误作答不直接产生负分，错误之后也不直接删除之前的有效关键点。它会消耗动作、时间或提交次数，并可能触发原游戏的失败条件，因此仍会影响最终结果。重复点击、反复打开同一页也不会刷出额外进度。

### 4.5 固定门和阈值组怎样计数

“门”指路线需要满足的关键条件，不一定是画面里的一扇门。路线可包含固定门和阈值组。固定门要求指定的点必须完成；阈值组表示一组候选点中完成足够数量即可，例如“3条证据中取得任意2条”。[S04、S08]

设H为本局已命中的critical点集合；路线r的固定门集合为F_r；第j个候选组为G_rj，要求至少k_rj个。已完成的有效门数h_r和该路线需要的门数d_r为：

```text
h_r = |F_r ∩ H| + Σ_j min(k_rj, |G_rj ∩ H|)
d_r = |F_r|     + Σ_j k_rj
```

|F_r|表示固定门的数量；|F_r∩H|表示其中已经完成的数量。min表示候选组最多贡献它要求的数量，完成更多候选不再增加该路线得分。

例：某路线要求固定门A、B都完成，并从C、D、E中完成任意2个。分母中的中间门数是d=2+2=4，不是5，也不是把整个候选组算成1。若当前完成A、C，则h=1+1=2；再完成D，h=3；再完成E，候选组仍只贡献2，h还是3；最后完成B，h才为4。

同一路线内固定门与各候选组不能交叉，候选组之间也不能重复计同一个点；组成员必须是critical，阈值不能超过组大小。不同路线可以共享关键点，但比较路线进度时不会把几条路线的分数相加。

### 4.6 Progress逐步计算示例

未完成最终目标时，在中间门之外多预留1个“最终成功单位”。当前公式是：

```text
若指定目标已完成：p = 1
否则存在d_r > 0的路线：p = max_r [h_r / (d_r + 1)]
否则：p = 缺失
```

继续使用上面的路线，d=4，未成功时分母始终为5。假设只有这一条路线：

1. 没有完成关键点：h=0，p=0/5=0，x=0。
2. 完成A和C：h=2，p=2/5=0.4，x=0。
3. 再完成D：h=3，p=3/5=0.6，x=0。
4. 再完成E，或完成一个optional支线：h仍为3，p仍为0.6，x仍为0。
5. 再完成B，中间门全部完成：h=4，p=4/5=0.8，x仍为0。
6. 最终目标被裁判确认：p=1，x=1。

因此，0.8不是“80%的概率能成功”，而是这个计分定义下的中间推进程度。预留的1个单位避免“全部中间步骤完成、最终目标未完成”也得到满分。若最终目标已经被可靠确认，p直接为1，不要求评分公式再去猜测成功，也不要求必须补做未被实际成功条件要求的门。

### 4.7 多路线与特殊情况

**多路线取最大值。** 例如路线甲有4个中间门，已完成2个，值为2/5=0.4；路线乙有2个门，已完成1个，值为1/3≈0.333。当前p取0.4，不取两者之和，也不取两者平均。

**成功路线与进度候选路线要分清。** 当前代码计算进度时遍历所有显式路线，不只遍历target_success列出的成功路线。例如甲有2个门、乙有1个门，二者共享的点已完成，则最大进度可能来自乙的1/2，即使乙的结局不算目标成功。路线集合必须在运行前审定，不能把进度等同于朝某个特定成功结局还剩多少距离。[S04]

**锁存反映本局历史。** 即使后来放弃了某条分支，其已经命中的点仍可能贡献历史最大路线进度。因此p不是当前状态下的可达成功概率，也不保证该路线仍可走通。

**没有中间门时不臆造部分分。** 没有可计路线且未成功，p为缺失，不是0；成功后p=1。对于没有显式路线、且用单结局作为目标的配置，实现会以全部critical点建立默认路线。有路线但d=0时，该路线不参与未成功进度的计算。

**失败不一定等于零进度。** 模型放弃、用完预算或进入终局失败，x为0，但此前获得的路线进度可以保留。若本来就没有可计路线，仍为缺失。SR与Progress分别保留“目标未完成”和“曾经走到什么程度”的信息。

### 4.8 怎样读运行结果里的字段

在target_v1下，单局summary中的progress来自裁判的route_progress，用于论文主Progress。checkpoints_reached和checkpoints_total是全题critical点的命中数与总数，跨多条路线统计；它们的比例不一定等于路线进度，因为路线可以共享点，也可能只要求候选组中的部分点。

代码还保留reasoning_progress等统计字段，它不是这里定义的论文主Progress，也不自动证明独立推理。route_id也不能单独说明哪条路线贡献了target_v1的最大进度；应结合完整路线和判分记录解释。结束原因ended_reason同样不是成功值：出现ending仍需检查target_success。[S04、S06]

## 5 多次运行怎样汇总成模型成绩

### 5.1 先按题平均 再按题等权平均

正式计划每题每模型3个独立有效局。题t第j局的目标成功值记为x_tj，路线进度为p_tj，计划重复数为n_t。T是主测题集；T_P是运行前确定、可稳定计算进度的题目子集。[S06]

```text
SR_t = (Σ_j x_tj) / n_t
SR_macro = (Σ_t∈T SR_t) / |T|
Progress_t = (Σ_j p_tj) / n_t
Progress_macro = (Σ_t∈T_P Progress_t) / |T_P|
```

例：某题三局成功值为1、0、1，则该题SR=2/3≈66.67%。三局进度为1、0.6、1，则该题Progress=2.6/3≈86.67%。第二局即使走到0.6，仍是一次未完成目标，不会因为已有部分进度而在SR中记成0.6次成功。

若另一题三局全部失败、但各有0.2进度，它的SR=0，Progress=0.2。只含这两题且都纳入T_P时，模型SR_macro=(2/3+0)/2=1/3≈33.33%；Progress_macro=(2.6/3+0.2)/2≈53.33%。每题等权，关键点多或流程长的题不会仅因此获得更大权重。

主表分别显示SR和Progress，以SR排序、Progress辅助比较，不相加。SR回答完成任务的频率；Progress回答按已定义路线取得了多少推进。它们的分母、题目范围和解释不同。

### 5.2 缺失数据怎样处理

有效失败和数据缺失不同。模型正常放弃、预算耗尽、错误作答或终局失败，属于有效局；目标没完成时x=0。API、网络、环境或裁判异常导致的局不按模型零分处理，应保留异常记录并按预先确定的规则重跑。

若计划3局只有2个有效局，当前正式汇总不把缺少的一局补0，也不直接用已有2局产生完整的逐题SR，而是把该题完整成绩标为空，并报告有效局数。所有主测题的重复都齐全，才输出完整SR宏平均。

Progress还要满足两项条件：该题在冻结清单中声明progress_scored=true；每个计划有效局的p都存在且在0到1之间。只要一局缺失，该题完整Progress就为空。预定进度子集T_P中任何题不完整，完整Progress宏平均也不输出。不能在看见某模型缺失后临时缩小它的题集，否则模型间分母不同。

### 5.3 pass³怎样衡量重复成功

pass³衡量“三次均成功”的稳定性，区别于“尝试三次至少成功一次”。若一题共运行n次，成功c次，且n≥3，则：

```text
pass³_t = C(c, 3) / C(n, 3)
pass³_macro = (Σ_t∈T pass³_t) / |T|
```

C(n,3)表示从n次中选3次的组合数。恰好运行3次时，成功序列1、1、1对应pass³=1；1、0、1虽有SR=2/3，但pass³=0。若运行5次、其中4次成功，则pass³=C(4,3)/C(5,3)=4/10=0.4。计划有效局不齐时不计算完整值。它是重复成功指标，不是用少量运行精确证明成功概率。

### 5.4 好结局率与终局失败率

好结局率只在运行前声明good_ending_scored=true的题目集合上计算，按各题好结局次数除以计划有效局数，再按题等权平均。终局失败率在terminal_failure_scored=true的题目集合上同样计算。两者都要求相应记录完整；未声明适用或没有等级信息，不解释成0。

例如某题三局分别是good、normal和没有结局，且记录齐全，好结局率为1/3；若三局中只有一局发生真实终局失败，终局失败率也是1/3。SR仍独立依据target_success计算。一个未达指定目标的normal结局、一个主动放弃和一个游戏死亡，都可能是SR=0，但其结局与失败字段不同。

### 5.5 按能力子集怎样计算

对预先标注需要能力a的题集T_a，先取得各题SR_t，再计算SR_a=Σ_t∈T_a SR_t/|T_a|。例如“状态追踪”子集由3题组成，逐题SR为1、2/3、0，则该子集SR=5/9≈55.56%。一道题可以属于多个能力子集，子集题数不能相加当成总题数。

可选能力均衡分为各能力子集SR的几何平均：balance=(Π_a SR_a)^(1/|A|)。例如4项子集SR为1、0.5、0.5、0.5，均衡分约0.595；任一项为0则结果为0。有子集为空或成绩不完整时不计算。这个辅助值反映是否偏科，主表仍以SR和Progress为主。

### 5.6 步数与预算怎样影响得分

步数、时间、token不是直接加减进度的分值，主要用于限制资源和比较效率。错误动作会花掉预算，但不在p里额外减0.1之类的分数。合法、非法和格式错误动作都消耗一步，wait也算一个动作；程序生成下一次观察不另算一步。

默认预算按正常参考轨迹动作数L分档：L≤20对应60步、60分钟；20<L≤50对应150步、120分钟；L>50对应300步、180分钟。逐题例外动作上限须在运行前记录依据并对所有模型一致，不能看过成绩后给某个模型单独延长。[S09]

专用submit_answer默认上限10次，这不等于网页内所有表单都只能提交10次。有效时间包括正常请求、动作和等待；记录的基础设施重试等待另行处理。当前初版规则允许单决策额外重试最多2次、异常整局额外重跑最多2次，不能因为模型正常失败而随意重跑取最好结果。

### 5.7 哪些运行能进入正式主表

汇总核对official标记、LLM策略、正常记录的终止原因、target_v1、冻结清单身份、题目配置与裁判SHA-256、输入方式、模型参数档案和重复编号。不符合条件的记录会排除并注明原因。同一题、同一模型、同一重复编号出现多个有效结果时会拒绝汇总，而不是自动挑一个高分局。[S06]

跨模型比较还需固定任务版本、初态、动作、观察历史和预算。当前主测计划为B档必传图、最近4步完整观察与最多2张历史截图、输出上限初版32768 token；采样保留各服务默认设置，可控制的推理档采用预定配置。参数不支持或无法完全对齐的差异必须事先记录。[S02、S11]

## 6 论文撰写建议与实验交接

### 6.1 现在可以组织的论文内容

引言可以描述多步交互解谜对证据整合、规划、状态追踪与交互控制的联合要求。方法部分可以完整说明任务定义、观察动作接口、玩家与裁判分离、目标成功与路线进度、预算与重复、异常和缺失处理。任务部分可以说明题目的来源、版本、完整作品或任务单元范围，以及各能力标签的定义。

结果部分应在正式实验后报告同题集下的SR、Progress、重复成功稳定性和能力子集结果，并结合轨迹解释失败发生在哪一环节。方法部分可以先按本文的任务定义、输入条件和评分规则组织。

可采用的方法概述文本：“我们将交互式解谜建模为带受限观察和动作接口的任务执行过程。智能体通过玩家侧信息选择动作，独立裁判依据环境状态验证指定目标与中间进展。评测分别报告按题等权的目标成功率和路线进度，并通过重复运行、版本校验及异常排除保证结果可审计。”

### 6.2 正式实验的最小闭环

1. 冻结任务清单，明确整作或单元范围、资源与裁判版本、目标、Progress适用性、能力标签和预算。核清同ID多版本关系，剔除夹具与纯冒烟任务。
2. 冻结代码、依赖和运行环境，并在执行同事环境验证独立包及重置。为L3准备可核查的在线状态策略。
3. 逐模型验证图像、参数、请求超时、返回解析与拒绝分类，保存参数档案指纹；不能把模型列表当作接入完成证据。
4. 在正式成绩揭示前完成小规模试跑、预算校准、异常与重跑规则；随后按相同任务条件执行每题3局，保留全部有效失败与异常尝试。
5. 使用冻结清单汇总，检查各题有效局、缺失、版本和重复槽位，再形成主表、能力子表与误差分析。

建议主表同时给出SR、Progress、完整题数/计划题数、有效局数与缺失数；次表给pass³及适用题集上的结局和失败指标，成本另列。可按语言、题型或能力子集分组，并结合轨迹分析失败环节；各项分析使用相同的B档主测条件和预定统计口径。

置信区间、跨模型配对比较和能力标签一致性检查属于后续统计设计，当前仓库汇总不自动提供这些结论。建议按题进行重采样并保留同题模型配对关系；多标签子集相关、题目规模不均及少量重复都会影响解释。
