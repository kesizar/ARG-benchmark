# ARG Benchmark 测评协议（草案 v0.1）

状态：待题集和运行参数冻结后生效；本文区分已有实现与正式运行前的要求。更新日期：2026-10-27。已确定的模型见 [测试模型名单](model_candidates.md)。

## 1. 测评对象和边界

测量模型在统一游戏环境中，通过玩家可见信息和允许动作探索、解谜及到达结局的能力。每个游戏根据自身条件选定适合的实现层，并在该游戏的所有模型运行中保持一致；不把 L1/L2/L3 当作同一个游戏需要逐层重复测量的自变量。主榜按冻结题集汇总，可按实际采用的实现层、观测档另行分组报告；分组结果受题目组成影响，不作为实现层因果比较。主测采用 B 档（可见文字、元素及截图）；A、C 仅在另行设计对照时报告。模型不可读取裁判、答案或攻略，不开放任意外网搜索。具体动作、题面和资源由冻结后的任务配置决定。游戏本身的公开程度可能带来训练数据污染，不能将分数等同于完全陌生题目的推理能力。

正式题集尚未确定。每条正式题须满足 [数据准备与验收](data_preparation.md)，并提供稳定原始行 ID、任务 ID、游戏版本、配置与裁判哈希、运行层、账号要求、重置方式和验收证据；夹具和冒烟任务排除。先冻结题集与纳入标准，再运行所有比较模型。

## 4. 单局执行和终止

启动游戏与全新上下文，提供题面和初始观测；每步模型输出动作，harness 校验并执行，裁判读取状态并锁存已命中点，随后记录动作、观测和判分。结束原因包括真实结局、终局失败、主动放弃、步数上限、时间上限及运行错误。失败不是通关；普通错误或可继续探索状态不是终局失败。答案采用 NFKC 归一化、去除空白、转小写后计算 SHA-256 比较；当前实现将正确提交计为通关及好结局；正式规则以指定任务目标为准，见第 6A 节，不能简单沿用。裁判和答案不进入模型消息。

真实结局根据裁判实际 hook 判定；多路线的 tier 为 good、normal、bad。只有裁判验证的 good 记好结局。结局、失败、进度和提交机制需逐题正反例验证。当前单局输出包括 summary、steps、judge、模型原始响应、截图及配置快照；日志可能包含私有题目信息或模型输出，应限制访问，发布前审核。

## 5. 计分机制：当前实现

记单局已锁存 critical 点集合为 H。某路线固定门集合为 F；每个门组候选集合为 G_j，要求命中数为 r_j。路线有效命中和总门数为：

```text
h = |F ∩ H| + Σ_j min(r_j, |G_j ∩ H|)
d = |F|     + Σ_j r_j
```

门组不得重复或与固定门重叠，且均引用 critical 点。optional 点锁存在侧记录，不计入 critical 总数；diagnostic 与 events 只作诊断。当前实现选择路线的规则：已到达结局时优先结局 tier（good > normal > bad），再比较 h、h/d；未到结局时从可选路线按 h、h/d 选择，普通门集合是另一普通路线严格子集的路线会被排除。相同键取配置中靠前路线。无显式路线时，以全部 critical 点组成 main 路线。详见 [judge.py](../harness/judge.py)。

对选中路线，设 O 为不在其门集合中的 optional 点，o 为其中已命中数：

- 未到选中路线结局：`progress = (h + o) / (d + |O|)`，分母为 0 则为空。
- 已到选中路线结局：`progress = h / d`；若 d=0 则为 1。故通关后不保证进度为 1，也不再计 optional。
- 没有选中路线且尚未通关、有 optional 点时：`progress = 命中 optional 数 / optional 总数`；否则为空。
- 仅答案无门的任务，正确答案后进度为 1。所有非空进度按实现四舍五入到 4 位小数。

路线判定根据结局 hook，而不是仅根据门数；到达所有门不自动构成结局。`checkpoints_reached/total` 是全题 critical 点计数，不能代替多路线进度。以上公式忠实描述当前实现；optional 在通关前后处理不同可能造成进度不连续，正式题集冻结前需审查是否接受此定义，若改规则须改代码、回归验证并升版本。

## 6. 汇总指标与有效性

对同一题集、模型、运行层及观测档，令有效局数 N，进度非空局数 M：

```text
通关率 = Σ 1(真实结局或正确答案) / N
好结局率 = Σ 1(tier = good) / N
终局失败率 = Σ 1(终局失败) / N
平均路线进度 = Σ 非空 progress / M（M=0 时不报告）
```

同时报告 N、M、每题结果、步数、用时、token、结束原因和失败数；不得把缺失进度当零。本节是现有汇总字段说明，不定义论文主表；正式主表按第 6A 节报告 SR 和 Progress，不合成单一总分；步数、时间及 token 为效率指标。现有汇总对有 `failure_reached` 字段的局计算失败率，历史缺失字段不假定为非失败。题目重复次数不等时，直接逐局平均会提高重复次数多的题的权重；正式报告应同时提供每题均值及按题等权的宏平均，且固定分母与覆盖范围。多次重复的结果应展示离散程度；跨模型只比较相同题集和条件。

模型合法地放弃、预算耗尽或进入游戏终局失败是有效结果；API、网络、裁判、游戏环境或数据缺失导致的基础设施错误不当作模型零分，保留原始记录与原因，按预先冻结的重跑政策在同条件下从新局重跑。若无法完成，标记缺失并报告覆盖率，不选择性丢弃失败。汇总入口只纳入显式标记为 official、LLM 运行、正常终止且裁判无错误的局；其他局和缺失 summary 的目录记录在 `.excluded.json`。历史未标记记录默认排除，不自动推断。原汇总仍是按运行局汇总；新增 `scripts/report_protocol.py` 按冻结题单和 target_v1 局生成逐题宏平均、pass^3 与能力子集，但尚需独立验收并核对清单与版本，保留原始文件。批跑当前串行且遇错继续；不可把进程成功退出视为每局有效。

## 6A. 本窗口讨论形成的正式测评设计（草案）

本节将论文报告方案与第 5、6 节的**当前实现**分开。用户已确认路线进度与指定目标的通关原则；本节选定预算、重复及模型参数初版，试跑前不得视为最终冻结。没有相应实现或验收之前，不能声称现有代码已按本节计分。

### 主表：按题等权的 SR 与 Progress

令冻结主测题集为 T，题数为 |T|；同一题 t 对每个模型的计划重复次数为 n_t。对第 j 次**有效局**，裁判验证完成指定任务目标记 x_tj=1，否则记 0；普通/坏结局但目标未完成均记 0。每题每次须从该题冻结的初始状态独立开始，记录环境随机性与模型参数；同题所有模型使用相同的实现层、观察档、任务版本及预算。

```text
SR_t = (Σ_j x_tj) / n_t
SR_macro = (1 / |T|) × Σ_{t∈T} SR_t
Progress_t = (Σ_j p_tj) / n_t
Progress_macro = (1 / |T_P|) × Σ_{t∈T_P} Progress_t
```

主表显示 SR_macro 和 Progress_macro，按 SR 从高到低排列；SR 相同时以 Progress 作为次序指标，不把二者相加。展示每题结果和有效局数。只在各模型均覆盖同一冻结题集、每题达到计划有效局数时称为完整主榜；部分缺失的模型单列实际覆盖率及每题结果。若另外计算共同有效题子集上的比较，须列出具体子集与分母，不能与完整主榜分数混称。进度缺失不视为零：Progress 只在预先定义并验收可计进度的题集 T_P 上计算，报告 |T_P|、名单和覆盖率；不能悄悄按不同模型各自可用题平均。答案型题若无法定义可验证的部分进度，可不纳入 T_P；已验证的成功局可记为 1，但不能据此把该题的失败局进度强行视为 0 或将该题部分纳入平均。

SR 回答是否完成任务；Progress 反映经过验证的路线推进，不保证模型已经通关。好结局率仅在事先明确有可比 good 结局且已验收的题目子集报告，附子集分母；终局失败率、动作数、时间、token 与费用分别作为诊断或效率数据，不合成为总分，也不能把未记录好结局的题默认为没有好结局。题目多标签时可在多个能力子集中出现，注明重叠，不把子集数量相加当作题集规模。

### 路线进度：已确认规则，待实现和验收

第 5 节现行规则将 optional 与必经门混合且通关后改变分母，可能跳变。用户已确认采用以下新规则，终局单位权重 1 为本协议确定的初版实现参数：固定任务中所有**有效、已验收路线**集合 R；对每条路线按第 5 节的固定门和阈值门组计算 h_r 与 d_r。仅使用已锁存、玩家可通过合法动作达成的必经 critical 门；optional 单独报告，不计入主 Progress。所有路线在开局前冻结；不因为本局表现临时增删候选路线。

```text
p = 1                                          若裁判确认完成指定任务目标
p = max_{r∈R, d_r>0} (h_r / (d_r + 1))         否则，存在可计分路线时
p = 缺失                                       否则
```

每条路线在 d_r 个必经门之外预留 1 个“完成指定目标”的终局单位，完成目标才可得到该单位。因此未完成目标时即使必经门全部完成也严格小于 1；成功由裁判验证，不由门数或进度推断。不同路线可以共用门；同一路线内部的门组与固定门仍不得重叠。锁存 H 只增不减、候选路线固定时，各路线比例及其最大值不会下降。上述最大值衡量“历史最佳已验证路线推进”，不保证被不可逆操作封闭的路线仍可完成；路线有效性须逐题验收，不能把该数解释为剩余成功概率。

示例：两条路线分别有 4 和 2 个必经门，当前命中数为 2 和 1，则进度为 max(2/5,1/3)=0.4；即使 4 个门全命中，未完成指定目标时该路线最高为 4/5。正确完成指定目标后记 1；没有可计分门且未成功时记缺失。

该方案已获用户确认。共享裁判已增加 `scoring_protocol: target_v1` 和显式 `target_success`，并保留旧裁判原有语义；新汇总入口只接收 target_v1。本地合成用例已覆盖成功、普通结局、可选点、缺失与阈值组等部分情况；各游戏仍需逐一配置和验收成功条件、路线、门组与重置，不能据此声称正式测评已就绪。正式结果不得混用旧分数与新分数。

### 能力子集与能力均衡分

在题集冻结前为每题标注其**主要通关所需**的 gating 能力；一个题可有多项标签。至少分别给出叙事证据推理、长程规划、状态追踪、交互探索的子集 SR；是否构成 gating 要有任务与裁判证据，不能仅根据题材、剧情或作者标签推断。冻结各能力的题目集合 T_a、标注标准和样本量；空集、定义不清或数据缺失的能力不计算均衡分。

```text
SR_a = (1 / |T_a|) × Σ_{t∈T_a} SR_t
能力均衡分 = (Π_{a∈A} SR_a)^(1 / |A|)
```

按用户此前选择，任一能力子集 SR 为 0 时均衡分为 0。该分只放附录或次表，用于观察是否偏科，主表仍以 SR 和 Progress 排序；各子集也单独展示，重叠题目和样本不足会影响解释。

这个零值敏感版本是**借鉴 Crafter 的跨能力几何汇总思路**，不是其原公式。Crafter 原论文使用带 `log(1+s)` 的平滑几何汇总，不能描述为“沿用 Crafter 原公式”。参考：[Crafter 原论文](https://arxiv.org/abs/2109.06780)。

### 重复运行与 pass^3（首版每题三次，试跑后冻结）

正式计划每题每模型独立运行 3 局；试跑后可在正式开跑前修改并冻结，正式结果揭示后不因模型成绩调整。受成本约束需要减少时仅可在开跑前整体修改并说明。令 c_t 为成功次数：

```text
pass^3_t = C(c_t, 3) / C(n_t, 3)
pass^3_macro = (1 / |T|) × Σ_{t∈T} pass^3_t
```

当 n_t=3 时，该值仅在三次全部成功时为 1，其余为 0；不足三次有效局记缺失并报告覆盖率。该估计假定同题重复在固定条件下可视为独立同分布，τ-bench 的无偏性是多次重复实验意义上的性质，不意味着三次实验就能证明结果不是偶然、也不等于每题成功概率的精确值。若环境或模型条件变化，独立性不成立，需披露且不能直接套用解释。pass^3 作为次表；不与只要一次成功的 pass@3 混淆。参考：[τ-bench 原论文](https://arxiv.org/abs/2406.12045)。

### 指定任务目标与通关判定（已确认）

SR=1 当且仅当裁判验证该局完成冻结题面指定目标。仅到达普通结局但未完成指定目标，或到达坏结局，均为 SR=0；好结局也须完成指定目标才能计为成功。若指定目标为提交答案，必须满足相应的答案条件，不因触发其他结局自动记成功。每题验收时明确目标、成功结局/答案、普通或坏结局以及终局失败的 hook；不能以已达门数、模型声称完成或结局类型字段替代目标验证。各局 SR、结局类型与终止原因分别保存。

### 从严验收与防止虚高（待逐题实现）

本 benchmark 优先选择有区分度的任务，并以可验证证据严格计分，避免提示泄露、碰运气和宽松裁判造成分数虚高。严格性服务于测量有效性，不根据预期模型排名或已观察成绩任意改变门槛。下列要求须在题目和结果冻结前落实；当前实现不会自动证明所有条件成立，未验收的游戏不能仅因资源可运行就进入正式主榜。

1. **明确任务目标**：题面先规定要完成什么，裁判只在客观成功信号出现后记 SR=1。只读到线索、到达中间页面、完成表单的一部分、模型自称成功均不能替代目标完成。未完成目标的 Progress 沿用上式，全部必经点完成仍小于 1。每个成功 hook 均须有真实正例及相似但不应成功的负例，并在独立新局复验。
2. **只计真实必经推理和状态**：critical 点须是与指定目标有关、通过可观测行为或可靠游戏状态证实的必要进展，须记录依赖关系、来源和正负例。访问页面、点击次数、可选剧情、直接复制显示的答案及自动触发的事件一般不计为推理门；一个联合问题不得为了提高分母而拆成缺少独立意义的多个点。原游戏没有必要经过的点不能人为称为必经点，否则可能误判合法通关。
3. **检查路线与锁存**：对互斥分支、回滚、重置和旧存档进行负例测试，确认门命中对应当前局、当前已验收路线，不能利用脏状态或跨分支组合夸大进度。当前 Progress 取历史路线最大值，不能识别所有不可逆封闭路线；若该限制会使某题的进度产生实质虚高，在代码和该题裁判修复、复验前，该题 `progress_scored=false`，其 SR 仅在成功裁判已独立通过验收时可保留。不得把缺失 Progress 算为零，也不得将历史最佳解释成仍可达目标的概率。
4. **检查提示、直接答案与试错**：验收时记录原游戏提示、错误反馈、答案空间和可重试次数，实际演示有无显著的猜测或答案直接暴露捷径。若捷径不能在保持任务有效且对模型一致的条件下控制，就不得声称该题通过完成与否验证了相应推理能力；必要时移出该能力子集或正式主榜，并说明原因。不能偷偷修改原游戏或在看过模型结果后临时收紧；如采用关闭提示、限制次数或其他改造版本，须事先写入题面及配置，证明题目仍可解并对所有模型统一执行，与原版分别版本化。现有 `submit_answer` 限额不等于游戏内表单限额，不能声称已限制后者。
5. **独立重复与覆盖**：按冻结计划报告每局结果、逐题 SR、Progress 和次表 pass³；三局中任何一局未成功，pass³ 为 0，但不足三局有效数据时为缺失。它是稳定性指标，并不证明偶然性被排除。有效模型失败不得选择性重跑或删除；基础设施故障也不得当零分。所有模型使用同一冻结题集、预算、观察条件及逐题标准。
6. **范围和可审计性**：每题保存目标、游戏版本、裁判版本、门及分支证据、正常完整解、负例、重置检查、提示与试错风险、可计分指标及能力标签依据。对答案短、明显可暴力枚举或游戏显示解答的任务，尤其不能仅凭通关给模型“推理成功”的解释。可选设置首次答案正确率、答案提交次数与提示使用率等诊断，只有在能够准确记录并经逐题验收后才报告；当前这些指标尚未实现，不用于主榜或更改 SR。

上述验收要求是本协议的拟执行规则，不代表目前的候选题已全部满足。题目准备窗口与测评窗口须对齐每题裁判和证据后再冻结；不能为压低数字随意加权、给失败结局以外的合法成功判零，或改变已确认的 SR、Progress 和 pass³ 公式。

### 预算、重复和异常处理：选定的首版

以下数值是研究团队确定的**首版正式计划**，并非论文直接给出的统一标准；首批题目和接口试跑后可在正式开跑前校准并一次冻结，正式结果出现后不得针对模型调整。参照 [τ-bench 原文](https://arxiv.org/html/2406.12045v1) 每题至少 3 次、最多 30 次 agent 动作，以及 [OSWorld 原论文](https://arxiv.org/abs/2404.07972) 的动作上限与环境重置；本项目长程游戏与其任务不同，不能照搬其步数。

- **重复**：每题每模型 3 个有效独立局，从冻结初态重新开始；同一模型同题 3 局均等权。无法恢复的基础设施异常不算有效局，标缺失并按固定完整题集覆盖规则报告；严禁根据通关与否选择重跑局。
- **动作与时间**：按任务准备者事先验收的正常参考轨迹动作数 L（含真实交互与必要提交，不使用非预期捷径；估计不可靠则人工审定并留证）定三档：L≤20 为 60 步/60 分钟；20<L≤50 为 150 步/120 分钟；L>50 为 300 步/180 分钟。L 是参考轨迹上界而非已证明全局最短；同题所有模型保持相同档位。游戏计时不得暂停的实时任务须额外验收，无法按本规则公平执行则暂不纳入主榜。冻结清单需记录 reference_steps 和 reference_evidence，正式启动及清单生成时校验配置的步数、时间和提交额度与档位一致。试跑观察是否系统性截断、超时或成本过高，正式前整体调整档位，不依据单模型正式得分改。
- **单题动作上限调整（2026-10-30 用户确认）**：上述三档是默认参考，不是不可突破的硬上限。根据具体任务的正常路线、必要交互和合理探索余量，可以为单题单独设定合适的动作上限，包括高于 300 步。题目配置与任务 spec 须一致记录上限、参考轨迹或人工估算、设定理由及待校准限制；人工估算不得称为实测。任务 spec 使用 `max_steps_override` 记录例外上限、`step_budget_override_reason` 记录非空理由，例外上限不低于参考步数；无例外时沿用三档。正式运行前确定并冻结，对同一题的所有模型使用同一上限，不依据正式成绩调整。时间和提交上限仍按既有规则处理，除非另行明确调整。
- **动作计数**：一次模型决策最多提交并执行一个动作；合法与非法动作、格式错误、重复操作均消耗 1 步，返回标准错误；模型等待和观察不额外算步。真实错误答案消耗次数。答案专用 `submit_answer` 默认 10 次/局，次数耗尽后返回明确提示；原游戏内部的逐关输入按游戏原规则执行，不与该接口限额混淆。确需超过 10 次的任务按其验证的必要次数加 2 次冗余，在试跑前记录并对所有模型一致。次数上限耗尽本身不强制终局；模型可继续其他合法动作直至目标、放弃、游戏失败或预算耗尽。
- **时间口径**：计入有效模型请求、生成、动作和游戏等待的累计实际时间；已记录的基础设施重试、限流退避和故障恢复暂停计时。另设每局墙钟保护上限为所选有效时间的 2 倍；达到墙钟保护上限时若由基础设施导致，标为异常缺失，不计作模型失败。每请求初版总时限为 900 秒，超时视为基础设施异常，迟到结果不得用于评分。正式模式使用独立请求进程实施总时限，到时终止并回收进程；进程启动及调度仍可能造成少量超时偏差，远端已处理请求仍可能计费。定时游戏按实际运行，故障期间无法公平隔离则从新局重跑。游戏动作本身仍无法保证执行中准时中止，需继续验收。
- **接口/局重试**：同一决策对网络连接错误、超时、HTTP 429/500/502/503/504 最多额外重试 2 次，退避 5 秒、15 秒，遵守更长的 Retry-After；其他服务端错误按分类处理。成功响应的格式错误不重试、不隐藏，计 1 步。重试耗尽后本局基础设施无效，从冻结初态最多重新运行 2 次；全部不成功记缺失，记录全部请求和局 ID、原因及耗时。鉴权失败、欠费、参数不支持、模型不存在等配置故障暂停该模型，修正并在正式运行前重新验收；不得悄然改参数继续计入同一批。API 却已处理写操作时，客户端需唯一请求标识并核对服务行为，避免重放动作；游戏动作不得因模型请求重试而重复执行。
- **异常归类**：模型显式放弃、无效动作累计耗尽步数、提交错误及有效预算耗尽、实际坏结局/失败属于有效局，完成指定目标才为 SR=1；API/网络/裁判/环境异常为无效局。模型安全拒绝且服务正常，记录为有效失败及拒绝原因；请求被供应商安全系统拦截但无模型有效输出时单列需人工审查，不随意归为零或故障。当前代码已调整 RuntimeError 不再一概转为 `_invalid`，正式 API 请求上限改为 3 次、批次增加最多 2 次网络故障整局重跑；仍需要验证全部供应商异常分类、请求去重、Retry-After 的日期格式、错误记录及整局重跑链路。当前已记录有效时间、基础设施等待和墙钟时间，并对重试与保护时限进行初步处理；已对 OpenAI 兼容显式 refusal 和 Anthropic refusal 做基础分类，其他服务商拒绝分类、启动故障完整记录、超时边界和端到端重跑仍需验收，不可宣称全部正式预算协议已实现。

### 模型运行参数：选定的首版

- **观测**：B 档；当前截图必传，最近 4 次完整观测、最多 2 张历史截图，旧动作保留结构化历史；上下文裁剪与笔记规则跨模型一致且记录。`require_images=true`，拒绝图片不静默降级；无法使用截图的模型单列，不纳入同条件主榜。
- **采样与推理**：正式主测不传 `temperature`、`top_p`、`top_k`，各服务采用其模型默认值并记录，不能宣称温度相同或确定性输出。可明确设置推理深度的模型采用该服务对应的 `medium` 或最接近的中档；无法调整/无可验证中档时保留默认并披露。不要把同名 medium 解释为计算量等价。支持思考开关且接口确认可控时启用思考；仅思考模型保持默认。各模型/端点采用唯一固定配置，不能同一主表不同任务换档。
- **输出**：每次请求输出上限首版 32,768 token，含服务计入该上限的推理 token；具体端点不支持时在正式前固定其允许上限并披露，不在失败后随意加大。记录 finish_reason、显式推理 token（服务提供时）、费用；输出截断计为模型未产生有效动作并消耗 1 步，除非服务故障导致中断。当前 1024 默认值不能代表本方案。记录厂商不提供推理 token 的缺失，而非记为零。
- **参数证据与缺口**：详见[模型参数核查附件](model_parameter_audit.md)。不同厂商对 temperature、thinking 和输出限制的处理不同；所有具体模型标识、截图、上下文、每项参数和权限均须在目标账户/端点实测。当前项目仅有 Anthropic Messages 与 OpenAI 兼容 Chat 路径；正式模式已省略温度并将输出上限默认为 32,768；OpenAI GPT-6 的 medium 和 Claude adaptive/medium 已加入适配，输出截断和缺图有基础检查，但其他厂商原生接口、思考参数及全部接口验收尚未完成，不能假定已正确适配各原生接口。完成适配和独立验收之前不应启动正式主测。

### 状态探索：有证据才报告

探索覆盖不是 SR，也不应直接由点击次数或页面访问量推断。若某题预先定义可达、去重并由裁判验证的有意义状态集合 E_t，单局状态探索覆盖为已首次到达状态数除以 |E_t|；无可靠枚举或无法重置验证时记缺失。先在预定义适用题集按题等权汇总，报告定义、权重、题数和覆盖率。此项为可选诊断指标，依赖状态清单和实现验收，**目前尚未实现或确定纳入正式主表**。

### 新协议接入示例（尚未完成验收）

在逐题审定后的私有裁判中显式配置：`"scoring_protocol": "target_v1"`；例如 `"target_success": {"route_ids": ["truth"]}` 指明仅 `truth` 路线完成目标。单结局裁判可配置 `{"ending": true}`，答案型题可配置 `{"answer": true}`，组合条件是“任一项满足”。坏结局不能列入成功路线。不能未经核实批量将旧 good/normal 结局改成成功；每题须有裁判证据。默认仍为 legacy，正式模式当前拒绝未明确迁移的裁判。

新版汇总命令 `python scripts/report_protocol.py --manifest <冻结清单.json> --runs <隔离运行目录> --out <报告.json>`。清单格式示例：

```json
{
  "id": "example-only-not-a-frozen-set",
  "obs_mode": "B",
  "repeats": 3,
  "required_capabilities": ["叙事证据推理", "长程规划", "状态追踪", "交互探索"],
  "models": [{"provider": "openai", "name": "example-model", "profile_id": "example-profile", "profile_sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"}],
  "tasks": [{"id": "example-task", "config_sha256": "bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb", "judge_sha256": "cccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccc", "reference_steps": 12, "reference_evidence": "example-not-real", "progress_scored": true, "capabilities": ["状态追踪"]}]
}
```

示例不是正式题单。当前汇总核对冻结题单、配置、裁判和模型参数指纹，检查重复局及未出现的模型；缺少有效重复则不计算完整榜分。模型档案摘要可用 `python scripts/show_model_profile.py --config <配置> --obs-mode B` 查询，随后写入冻结清单；逐题指定配置后可用 `python scripts/prepare_protocol_manifest.py --spec <规格.json> --out <新清单.json>` 计算配置和裁判文件哈希并生成清单。正式运行时设置 `LLM_EXPERIMENT_PROFILE`，实际模型参数与清单档案指纹必须一致。正式批次加 `--manifest`，单局还需 `--repetition`。数据资源、模型快照、提示词实现及运行环境的完整版本锁定仍需补齐；不能仅靠此命令认定报告已达到论文要求。旧 `aggregate_runs.py` 保留用于历史汇总，不可混同为新版主榜。

```powershell
.venv\Scripts\python scripts/validate_config.py configs/<任务>.json
.venv\Scripts\python scripts/run_one.py --config configs/<任务>.json --policy llm --obs-mode B --run-kind official --manifest <清单.json> --repetition 1
.venv\Scripts\python scripts/run_batch.py --set configs/<正式题集>.json --policy llm --obs-mode B --run-kind official --manifest <清单.json>
.venv\Scripts\python scripts/aggregate_runs.py --runs <隔离的运行目录> --out <输出目录>/aggregate.csv
```
