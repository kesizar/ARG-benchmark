# 正式数据准备与验收

范围为原始清单的 748 条记录，不按作品名去重。旧的“完成”清单仅作为已有配置索引，不能替代本流程。

用户最新交付口径（2026-10-29）：只交付符合测评协议、可实际计分的资源包，不按游戏来源或“旧包补齐/新增游戏”分别汇报数量；内部阶段状态用于执行管理，不能代替交付成果。

## 每条记录的交付

每条记录保留稳定原始行 ID，并关联一个或多个明确版本的游戏任务。逐项记录以下状态，不能把其中一项完成等同于整条完成。

1. 资源：确认原始入口、完整材料、运行依赖和账号条件。L1 保存本地资源及哈希；L3 记录真实服务依赖和可用性条件。连接失败、缺少资源和站点确定失效分别记录。
2. 接入：提供可直接调用的配置、启动/停止方法、重置方法及依赖版本。游戏资源和评测基础设施分离，API 密钥不进入资源包。
3. 内容：梳理所有可操作路径、对错判断、支线、正式结局、失败和退出。记录源码或实机证据，不拿翻页或普通收集代替推理解谜。
4. 裁判：明确每个点的成功条件、前置条件、锁存方式及路线归属。多条路径能绕过的门不能误标成每条路线必经。结局等级以原作证据和用户规则为准。
5. 实机：用正常界面/解释器动作走完整流程，检查成功得分、失败不加分、切换场景和重置。源码读取只用于裁判侧审核，不提供给模型。
6. 交付：从交付包解压到独立目录，在新端口和新上下文中运行，验证配置、材料及裁判不依赖原工作目录。记录所用基础运行环境；独立目录测试不等于跨操作系统测试。
7. 复核：单独处理谜题歧义、跳过漏洞、外部不稳定因素和难度问题。工程可运行与适合正式计分分开标记。

## 保守判分原则（2026-10-28 用户确认）

在有证据支持的合理范围内采用保守判分：只有本局真实操作及可核查的答案或状态满足预先写明的成功条件，才授予相应分数。页面出现、跳转或宽松的原作门槛本身不能证明答案正确；若裁判无法区分正确答案和错误答案，保留为诊断并补齐观测或验证，不能据此授分，也不能把无法观察的正确答案直接判错。

正确答案的等价形式以题面和来源证据为依据，统一规范空白、大小写等无关差异；有证据支持的其他正确解也应得分。答案歧义或来源不足时记录原因并暂不将该点作为已验证的正式计分点，不能为了压低分数排除已证实的正确解。提示、猜测和重试本身不自动使游戏不可评分：如使用提示或重试影响分数，必须由运行前固定、公开且可实际观测的规则决定，并分别记录；不得事后臆测模型是否猜到或独立推理。完成指标不能表述为独立推理能力，未核验的推理点和路径仍需明确留作缺口。

新规则适用于新建和修复裁判；既有结果须按受影响行为复核，禁止静默改写历史成绩。每次变更保留版本、评分范围与正负验证证据。

用户确认：若玩家在作答前已看到游戏直接给出的完整答案，照抄或提交该答案不能表述为独立推理；此前已标可计分的完成指标保留。仅提供线索、规则或可选提示不自动排除题目：需要按玩家实际看到的内容及事先公开、可观测的计分规则处理；无法区分答案是否已经展示时，不应无条件声称该次作答证明推理。保留旧包、原始状态和历史成绩。

## 资源包的四项评测准备（2026-10-29 用户确认）

后续制作资源包时按 [测评协议](evaluation_protocol.md) 一并准备：指定任务目标及成功判定（SR）；路线、关键点及 Progress 配置；结局类型及终局失败记录（确无对应类型时标明不适用，信息不足标明未注明）；整理已有能力标签供正式题单使用。沿用已有标注，不重新判断对错或重复测试；无法从已有记录确定的字段标明缺口，不凭空推断。已有包参考 [四项字段缺口清单](../data/preparation/reviews/four-metrics-gap-list-20261029.md)，通过共享队列领取和分工，避免重复处理。保留此前已标可计分、答案直接展示的完成指标，但不表述为独立推理。

## 包的两种边界

游戏资源包只包含可供玩家访问的作品文件。独立评测包还包含任务配置、裁判和对应版本的共享 harness；这些评测侧文件不得由游戏服务器托管。Python 包、浏览器或解释器等基础依赖记录版本和安装方法，不假装已随 ZIP 附带。

## 失败与通关

游戏确有不可继续的失败或死亡结算时，在私有裁判中通过 `terminal_failures` 显式声明，例如 `[{"id":"timeout", "hook":"timeout_visible", "op":"truthy"}]`；hook 仍须验证本局真实可见的失败状态。命中后评测循环以 `ended_reason=failure` 结束，记录 `failure_reached`、`failure_id` 和 `failure_step`，不将其记作 `ending_reached` 或通关。普通错误反馈、可重试状态及可继续探索的支线不能声明为终局失败。

该声明是新增、按任务启用的接口，旧裁判和旧结果不会自动重分类。历史 summary 若没有 `failure_reached` 字段，汇总时不假定它不是失败；失败率只对明确包含该字段的运行计算。若失败与通关标记可能同时出现，裁判需通过实际可见的前台结算状态消除歧义，避免遮罩后的模板文字导致误判。

当前 `scripts/build_prepared_bundle.py` 支持本地静态托管的浏览器任务，生成 `packs/<id>.prepared.zip`。它不适用于文字冒险解释器或自定义后端，相关类别需按实际适配方式补齐交付；不会套用网页模板后宣称完成。

## 用量控制（用户已确认）

保留上述全部交付与验收标准，优先减少重复上下文、重复阅读和无效调试，不用降低覆盖范围节省用量。

- 当前代理完成手头游戏后保存简短交接；下一游戏优先使用 `fork_turns="none"` 的新代理，仅提供规范路径、原始记录 ID、独占路径/端口、已落盘证据与待办。保持现有模型设置，不擅自降低模型强度。
- 深入分析前先用脚本检查资源完整性、截断、外部依赖和访问条件；候选筛选不算可用证明。明确阻塞时保存证据和恢复材料后继续其他条目。
- 先提取源码结构，再精读相关函数和分支；完整日志写文件，工具输出只保留摘要和错误附近。子代理只报告结果路径、重要风险及共享阻塞，不逐步转述常规操作。
- 复用启动、重置、操作与打包校验工具；重复失败先定位原因，不盲目重跑完整流程。
- 按实际差异复验。游戏、裁判、运行时或验收逻辑变更需验证受影响行为；纯说明修改可以逐文件等价证据加解包/启动检查连接原完整 UI 证据，明确复用边界。
- 主代理复核关键判分、覆盖范围、证据和交付包一致性，不重新做已经有充分证据的全部分析。减少并发不等于降低总用量，仍最多主代理加三个子代理。
- 用户已确认提速：任务完成或失败后尽快复核与补位；活跃轮次优先按代理完成事件推进，10 分钟心跳仅兜底，不作为批次节拍。全部任务仍运行且无新证据时立即安静结束检查，不反复读源码或轮询。新任务先从原始清单的“能获取可用”记录选择；源码齐全、复杂或需要恢复的作品均可处理，不因复杂度安排原始清单中“条件可用”的新任务。这个历史标记只是排序依据，每条仍须核实实际资源和依赖；发现不可用则留证据并转下一条。已开始的验收修复继续完成。
- 源码分析优先使用脚本建立状态、条件、跳转和结局索引，再针对相关源码片段判断谜题和裁判，减少整文件反复输入。可脚本化的界面操作和确定性校验由本地程序执行，输出简短摘要；源码推断仍需对应的正常界面或解释器正负验证、完整结局和独立包验收，不以静态分析替代实际验证。

## 先全面分析，再集中验收（2026-10-29 用户确认）

用户补充：遇到缺资源、访问受限或其他当前无法解决的阻塞时，必须保存已经取得的工作成果和可恢复的交接记录，供用户补充后从断点继续。交接记录应指明原始记录 ID、作品和版本、缺少的具体资源或条件、来源或原始 URL、已尝试的步骤及结果、已有资源/配置/裁判/候选包与验证证据路径、版本或哈希、已完成部分、尚未完成部分、恢复后的下一步。保留原件和已生成文件，不将未完成状态标为验收通过；用户补齐后先核对版本与对应缺口，复用未受影响的成果和证据，只处理新增资源影响的部分，不重做整项工作。

- 对选中的作品，先用脚本尽可能完整地扫描资源、依赖、交互入口、状态与跳转条件、答案判定、提示、失败和结局，并保存可定位到原文件的索引。脚本不能确定动态行为或未支持的格式时，明确标记遗漏，不把扫描结果当成完整性证明。
- 然后集中精读相关题面及前后文、判定代码与路线，区分线索、已直接给出的答案、真实推理点和普通操作，整理各节点的前置条件、分支和裁判依据。建立覆盖清单，区分源码推断与已有实机证据，一次列明缺口及需要验证的行为。
- 裁判编写直接依据集中扫描和精读得到的题面、源码及上下文，一次确定正确答案、可接受的等价答案、前置条件和打分点，并简要记录对应位置以便复核。不设单独搜集、扩写或展示“线索支持”的步骤；只有答案或评分条件存在实际歧义、无法客观判定时才针对缺口补查，仍无法确认则记录原因，暂不将该点标为已验证或对未经确认的答复授分。
- 分析完成后，按覆盖清单规划一轮集中验收：合并共用前缀的路线，使用可复现的状态或存档，覆盖真实推理点、全结局、失败支线、正常界面或解释器正负判定、接入和重置，以及独立目录解包部署。每项记录对应证据；源码推断不能直接冒充实机验证。
- 验收中出错先定位原因并保存已成功的结果，从可靠的检查点恢复，只重测受影响行为；未改变的资源、裁判和环境可复用可核对的既有证据，写明版本和适用范围。不得因单个控件、脚本或局部证据缺口而无条件从头重跑整条路线，也不为追求形式完整反复补测同一行为。
- 若必要验证因技术或资源条件无法完成，记录具体缺口和阻塞，暂不宣称正式评分就绪；复杂作品若近期无法闭合，保存分析和检查点后转向更易完成的候选。
